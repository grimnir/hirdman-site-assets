Reverse check

From one record to every door it opens

Scroll to follow one breached login through the rounds our analysts run.

1

A breach lists one corporate login. The password was changed and the ticket closed. We take the identifiers out of the record: login, mailbox name, password pattern, unique domain.

2

Round one: the same mailbox name turns up on a personal address and at a previous employer.

3

Round two: a username that mutates by the same rule, and a shop registered with the work e-mail and the same password.

4

Round three: the shop's password opens the corporate portal, and an admin login without e-mail appears. This is the path a monitoring feed never shows.

5

Every link gets a fix and a priority: unique passwords, passkeys and a second factor on the portal, the admin account closed.

From a recent engagement

No leaked password on the domain. Keys to production in a public file.

During attack-surface reconnaissance we found a UI development tool on two of the client's subdomains. Its version compiled the environment file into the public bundle: tokens for repositories, cloud roles, databases and storage.

The domain had no leaked e-mails or passwords, so a monitoring feed would have shown nothing. The vulnerability is rated only Medium by CVSS (5.3), yet the file held live keys. One token confirmed repository access. The client was notified at once and rotation of every secret started right after.
