Hirdman Radar for Burp Suite: leak counts for every subdomain

Hirdman Radar is a free Burp Suite extension. Give it a domain and it finds the subdomains, then shows how many leaked records mention each host: infostealer logs, work email addresses, credentials from breaches and records in breached databases. The numbers appear in Burp next to the traffic you are testing, and hosts with findings get Burp issues.

Hirdman Radar 0.1.0 · Release · News · Our Tech · November 2026

WhyA stolen login is part of the attack surface

A test usually starts from a few domains in scope, and the work moves to the subdomains behind them: mail, VPN gateways, single sign-on, staging. Some of those hosts already have a history. An infostealer on an employee's computer takes the saved passwords, cookies and live sessions, and every host in that list ends up in a stealer log. A stolen session cookie can get past MFA, and a password reset does not always end it.

That history changes where you look first. A VPN gateway with thousands of stealer records is a different target from a marketing site with none, and the count belongs in the report either way. Hirdman Radar puts it in Burp, next to the host. We wrote about subdomains as the starting point of external security in Analysis of Subdomains.

How it worksFrom a domain to issues in Burp

  1. Start from a domain or a requestType a domain on the Hirdman Radar tab and click Check for leaks. Or right-click a request in Proxy, Target, Repeater or Logger and choose Find subdomains and check for leaks.
  2. The server finds the subdomainsIt queries four sources in parallel, Certificate Transparency logs among them, merges the lists and drops infrastructure names such as mx, smtp and ns.
  3. The important hosts go firstMail, remote access and sign-in come first (mail, owa, vpn, sso, adfs, citrix), then internal systems (gitlab, jira, jenkins, grafana), then APIs and test environments. A domain scan checks up to 400 of them. The rest wait in the table as Not checked yet, and one button sends them for a check.
  4. Results fill the tableHosts with findings get Burp issues. Login pages are marked from responses Burp has already received: the plugin itself never contacts the hosts.

The tableWhat you see for each host

Risk
The highest level among the host's findings.
Scope
Whether the host is in Burp's target scope.
Infostealer
Infostealer log records that mention the host.
Work
Breach records with work email addresses.
Personal
Breach records with credentials for the host, whoever they belong to.
DB rec
Records in breached databases that mention the host together with an email or URL.
Latest breach
The newest known breach date among the 10 largest sources. Stealer logs and some sources carry no date, so a newer breach is possible.
Login page
A password form, HTTP authentication or a known gateway path (FortiGate, Cisco, Ivanti, GlobalProtect, Citrix, Outlook on the web, AD FS, Keycloak) seen in Burp's traffic.

You can filter the rows (With leaks, Not checked yet, Check failed, In scope), export them as JSON or CSV, or copy a Markdown summary into the report. Results are saved in the Burp project and are still there after a restart, offline too.

IssuesFindings in the site map

Each host with leaks gets an issue at https://<host>/ for every kind of finding: infostealer records, work email addresses, credentials for the host and presence in breached databases. Confidence is Tentative, because no analyst has verified the numbers. The issue carries the count, its sources, the date of the check and a link to the latest scan of the domain on scan.hirdman.pro.

In the settings you choose whether issues are created automatically, whether out-of-scope hosts get them, and the lowest severity worth an issue.

PrivacyWhat leaves Burp, and what stays

  • Only the names you choose. Domain and host names go to one server, the Server URL in the settings (https://scan.hirdman.pro by default), through Burp's own HTTP stack and its upstream proxy settings.
  • Nothing from the traffic. Requests, responses, cookies and paths stay in Burp. The plugin sends nothing to target hosts and never changes the scope.
  • Counts come back, without accounts, passwords, raw records or dumps.
  • Background checks are off by default. New in-scope hosts from your traffic are checked only if you turn that on.
  • Private project. Tick it at the bottom of the tab and the plugin sends nothing for that project; a running job stops before its next request.
  • Source available. The code is on GitHub, so you can read what the plugin sends before you install it.

LimitsFree, with limits per address

Free use lets you check up to 50 hosts at a time and 300 hosts an hour from one address, and rescan a domain once an hour. A domain scan does not count against the hourly host limit. The tab shows the current limits and, before a large check, how long it will take. A check that reaches the hourly limit carries on by itself while Burp is open.

InstallGetting it into Burp

  1. Download the jarGet hirdman-radar-0.1.0.jar from the releases page. The release lists its SHA-256.
  2. Add it to BurpOpen Extensions › Installed › Add, choose the extension type Java and select the jar. Burp Suite 2026.7 or later.
  3. Check a domainOpen the Hirdman Radar tab, type a domain and click Check for leaks.

The source is published under PolyForm Shield 1.0.0: you can use the plugin on paid engagements, read the code and build the jar yourself.

Beyond the countsWhen a number needs names behind it

The plugin runs a partial check, about a third of a full HIRDMAN review. It tells you how many records mention a host. A full review names the affected devices and employees, which sessions are still live and for which services, and what to close first.
